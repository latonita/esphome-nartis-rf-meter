# esphome-nartis-rf-meter

Компонент ESPHome для связи со счётчиками электроэнергии **Нартис И100 / И300** по радиоканалу **433 МГц** с помощью ESP32 и радиомодуля **CMT2300A** или **CC1101**.

Компонент заменяет собой выносной цифровой дисплей **Нартис Д101**: он **сопрягается** со счётчиком и далее **регулярно опрашивает** счётчик по протоколу **DLMS/COSEM**, забирая нужные показания по их OBIS-кодам. Полный список кодов можно найти в руководстве по эксплуатации дисплея Нартис Д101, а также приборов учета электроэнергии Нартис И100 и Нартис И300.

**ВАЖНО**: ПУ с дисплеем **Нартис Д101-2**, а также работающие по протоколу **RF-433-2** (большинство с 2024 г.в.) работатают с другими компонентами:
[Нартис RF433-2](https://github.com/latonita/esphome-nartis-rf-2-meter) или [Нартис UART RF433-2](https://github.com/latonita/esphome-uart-nartis-rf).

# Функции

## Реализованы

- **Активный опрос** счётчика по интервалу (`update_interval`).
- **Сопряжение (pairing)** со счётчиком: эмуляция probe -> ACK -> SESSION_SETUP -> подтверждение, как делает настоящий CIU.
- **Шифрование AES-128-GCM**; сессионный ключ автоматически извлекается из ответа счётчика при сопряжении (на основе серийного номера счётчика).
- **Автоматическое восстановление**: при сбое цикла компонент возвращается в ожидание и повторяет попытку на следующем интервале; после нескольких неудачных чтений подряд - автоматически выполняет повторное сопряжение.
- **Чтение пакетами** (`batch_size`) через DLMS get-request-with-list - несколько OBIS за один запрос.
- **Числовые и текстовые сенсоры** по произвольным OBIS-кодам и классам COSEM.
- **Авто-выбор канала** по RSSI или фиксация канала вручную.
- **Сохранение сессии в NVS**: ключ, счётчики кадров, адрес счётчика сохраняются во flash и восстанавливаются после перезагрузки - сопряжение заново не выполняется.


## Ограничения 

- Автоматическое масштабирование значений не происходит, т.к. счетчик не передает данные scaler/unit. Используйте `filter: - multiply: xxx`
- Опрос счетчика занимает в среднем около 30 секунд - не рекомендуется делать опрос чаще, чем раз 5 минут, дабы не засорять эфир

# Аппаратное обеспечение

Понадобится плата на **ESP32**, радиомодуль с антенной 433 МГц и серийный номер счётчика.
Работа с **ESP8266** не проверялась, но компиляция проходит.

# Радиомодуль - блок `radio:`

Радиочасть выбирается в YAML. Сам протокол от чипа не зависит: 2-FSK, 2400 бод,
девиация ±6 кГц, синхрослово `55 55 F6 72` (в эфире), порядок бит - старшим
вперёд. Меняется только кремний под ним.

| `type` | Чип | Состояние |
| --- | --- | --- |
| `cmt2300a` | CMOSTEK CMT2300A (например **XL2300-SMT**) | **по умолчанию**, проверен на живых счётчиках |
| `cc1101` | TI CC1101 | новый, **на железе ещё не проверен**, передатчик слабее на ~4 дБ |

## `type: cmt2300a`

Модуль использует нестандартный **3-проводной SPI**, поэтому обмен реализован
программным («bit-bang») SPI через обычные GPIO; аппаратный `spi:` не нужен.

| CMT2300A | Параметр | Обяз. | Описание |
|---|---|---|---|
| SDIO | `pin_sdio` | да | данные SPI (двунаправленная) |
| SCLK | `pin_sclk` | да | тактовый сигнал SPI |
| CSB | `pin_csb` | да | Chip Select (банк регистров) |
| FCSB | `pin_fcsb` | да | FIFO Chip Select |
| GPIO3 (INT2) | `pin_gpio3` | да | прерывание FIFO - **обязательно** |
| VDD | - | - | питание 3.3 В |
| GND | - | - | общий провод |

Линия **GPIO3 (INT2) обязательна**: по ней отслеживается заполнение FIFO при приёме,
и это единственный сигнал приёмника на этой плате (регистры флагов FIFO читаются как
`0xFF` и непригодны). Компонент проверяет её при старте и пишет результат в лог.

```yaml
  radio:
    type: cmt2300a
    pin_sdio: GPIO23
    pin_sclk: GPIO18
    pin_csb: GPIO27
    pin_fcsb: GPIO26
    pin_gpio3: GPIO14
```

## `type: cc1101`

Обычный 4-проводный SPI, тоже программный - аппаратный `spi:` не нужен.

| Параметр | Обяз. | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `pin_sclk` | да | - | тактовый сигнал SPI |
| `pin_miso` | да | - | данные от чипа (он же GDO1) |
| `pin_mosi` | да | - | данные в чип |
| `pin_cs` | да | - | выбор чипа (CSn) |
| `pin_gdo0` | **нет** | - | точный признак конца передачи; без него драйвер опрашивает состояние по SPI |
| `rx_offset` | нет | `0Hz` | подстройка частоты приёма, **со знаком**, в герцах: `-3kHz`, `2500`, `0Hz`. Диапазон ±200 кГц |
| `output_power` | нет | `10` | мощность передатчика в дБм, -30…+10 (см. ниже) |
| `bandwidth` | нет | `101562Hz` | полоса приёмного фильтра, 58 кГц…812 кГц (см. ниже) |
| `deviation` | нет | `6kHz` | девиация FSK, 0.5 кГц…200 кГц. **6 кГц - значение протокола**, менять без нужды не стоит |
| `modulation` | нет | `2fsk` | форма передаваемого сигнала: `2fsk` или `gfsk` (см. ниже) |
| `foc_carrier_sense_gate` | нет | `false` | подвязать петли подстройки частоты и битовой синхронизации к детектору несущей (см. ниже) |
| `sync_word` | нет | `0xF672` | два байта, которые ищет коррелятор: старший уходит в эфир первым. Менять почти никогда не нужно (см. ниже) |

В отличие от CMT2300A, здесь **нет обязательной линии прерывания**: состояние FIFO
читается по SPI точным счётчиком байт. `pin_gdo0` стоит завести, но без него всё
работает.

```yaml
  radio:
    type: cc1101
    pin_sclk: GPIO18
    pin_miso: GPIO19
    pin_mosi: GPIO23
    pin_cs: GPIO5
    pin_gdo0: GPIO22        # необязателен
```

Частотные параметры принимают запись с единицами (`6kHz`, `101562Hz`) и голое
число - оно всегда читается как герцы.

### `bandwidth` - почему 101562 Гц, а не 58 кГц

Полоса выбрана **не под сигнал**: по Карсону он занимает всего ~17 кГц (±6 кГц при
2400 бод), и даже самый узкий фильтр чипа, 58035 Гц, пропустил бы его с запасом.
Полоса выбрана **под уход частоты**: автоподстройка CC1101 работает только в
пределах ±полоса/4, а пара кварцев 20 ppm + 20 ppm на 433.8 МГц даёт до ±17.4 кГц.
58 кГц - это ±14.5 кГц, не хватает; 101562 Гц - это ±25.4 кГц, хватает.

Плата за это - примерно 2.4 дБ чувствительности. На сильной связи можно попробовать
`bandwidth: 58035Hz` и сравнить долю ответов с сошедшейся CRC.

### `modulation` - форма сигнала при передаче

`2fsk` (по умолчанию) - нефильтрованная 2-FSK: именно так принятый сигнал
раскладывается на SDR, и этого достаточно. `gfsk` - гауссова фильтрация BT = 0.5,
ровно то, что передаёт **настоящий** дисплей Д101 (это записано в его заводском
профиле RFPDK). Настройка влияет **только на передачу** - на приёме оба варианта
демодулируются одинаково. Имеет смысл попробовать `gfsk`, если счётчик нас не
слышит: та же мощность укладывается в более узкий спектр.

### `foc_carrier_sense_gate` - ручка для первого запуска на железе

Это настройка **пусконаладки**, а не повседневная. Она решает, работают ли петли
подстройки частоты (FOC) и битовой синхронизации постоянно или ждут детектора
несущей:

* `false` (по умолчанию) - `FOCCFG = 0x16`, затвор выключен. Петли подстраиваются
  непрерывно. Риск: пока мы долго ждём ответа счётчика - а при сопряжении это
  секунды - они подстраиваются под **шум** и успевают уползти к своим пределам
  (±25 кГц при полосе по умолчанию).
* `true` - `FOCCFG = 0x36`, затвор включён. Петли заморожены, пока не сработает
  детектор несущей. Риск: слабая преамбула может его не поднять - и ответ будет
  потерян целиком. Счётчик шлёт 10 байт преамбулы, это 33 мс при 2400 бод: есть что
  потратить, но немного.

Из даташита ответ не следует. Проверять надо измерением: посчитать долю ответов
**с сошедшейся CRC** при обоих значениях за несколько десятков циклов. Само по себе
появление байтов в FIFO ничего не доказывает - сорвавшаяся петля тоже наполняет
FIFO, только мусором.

### `sync_word` - когда его стоит менять

Синхрослово протокола - четыре байта, и в эфире они идут в порядке
`55 55 F6 72`. Первые два байта - это тот же `0x55`, что и преамбула, поэтому они
с ней попросту сливаются, и коррелятору остаётся найти ровно два байта: `F6 72`.
Они и лежат в паре регистров `SYNC1/SYNC0` (точное совпадение 16 из 16 бит), а
число байт преамбулы выставлено в 12. Получается `55` ×12, затем `F6 72`, затем
длина кадра - **байт в байт то же самое, что передаёт настоящий дисплей**: он шлёт
10 байт преамбулы плюс два байта `55` из синхрослова.

Ни при передаче, ни при приёме через FIFO не проходит ничего лишнего: весь
заголовок формирует пакетный движок чипа.

**Почему ключ вообще есть.** Порядок байт синхрослова здесь *выведен*, а не
подсмотрен в эфире. Он следует из правила заполнения `SYNC_VALUE` в CMOSTEK AN143
(байты заполняются сверху, поэтому `CUS_PKT13` уходит в эфир первым, а `CUS_PKT10`
последним), применённого к дампу регистров настоящего дисплея, и перепроверен на
ветке RF433-2, где драйвер CMT2300A доказан железом. Точное подтверждение даёт сам
экспорт RFPDK: заявленное там `Sync Value = 0x555555F6` раскладывается в регистры
ровно так, как они выглядят в дампе шины. Но **ни один SDR-разбор RF433-1 этот
порядок пока не подтвердил**, и файл `fw/RF_PHY_SPEC.md` §11 держит это открытым
вопросом; более того, §4.4 того же файла (и `FRAME_HEADER_SPEC.md:823`) печатает
обратный порядок `72 F6 55 55` - это листинг регистров `PKT10..PKT13`, прочитанный
как эфирная последовательность. Считайте его ошибкой документации.

Поэтому: если **ничего не принимается вообще** - ни одного байта, ни при каком
значении `foc_carrier_sense_gate`, - попробуйте `sync_word: 0x72F6`. Это
единственное альтернативное значение, которое имеет смысл, и оно стоит одной
строки YAML вместо пересборки прошивки.

**Почему 16 бит, а не 32.** `fw/RF_PHY_SPEC.md` §4.4 предлагает «вариант A» -
32-битное синхрослово `0x72F65555`. Даташит CC1101 закрывает этот вопрос
независимо от порядка байт: отдельного 32-битного регистра у чипа нет, а режим
`MDMCFG2.SYNC_MODE = 011/111` **не берёт вторую пару регистров - он повторяет
первую**. Коррелятор искал бы `F6 72 F6 72`, чего счётчик никогда не передаёт, и
ни один ответ не был бы принят. Настоящее четырёхбайтовое синхрослово на этом чипе
просто непрограммируемо - и при верном порядке байт это ничего не стоит: два
«недостающих» байта - это `55 55`, то есть преамбула.

> ⚠ **Мощность.** CC1101 в диапазоне 433 МГц выдаёт максимум около **+10 дБм**,
> тогда как настоящий дисплей Нартис Д101 передаёт **+14 дБм**. То есть наш запрос
> уходит примерно на **4 дБ слабее**: приём от счётчика не страдает, а вот
> «докричаться» до него получится не всегда. Запас заметно лучше, чем у ветки
> RF433-2 (там отставание ~10 дБ), но если связи нет - помогает модуль CC1101 с
> внешним усилителем (PA), а не увеличение `output_power`: выше +10 дБм чип всё
> равно не умеет.

> ⚠ **Зрелость.** Ветка CMT2300A отлажена на живых счётчиках. Ветка CC1101
> написана по измеренному описанию PHY (SDR + заводской профиль настоящего
> дисплея), но **на железе пока не проверена**. Если выбираете чип впервые -
> берите CMT2300A.

> GPIO в примерах выбраны как образец - подставьте пины своей платы. Входные линии
> (`pin_gpio3`, `pin_miso`, `pin_gdo0`) можно завести на любой вход; на ESP32 для
> этого подходят и пины 34-39 (только вход).

```yaml
external_components:

```

# Быстрый старт

```yaml
external_components:
  - source: github://latonita/esphome-nartis-rf-meter
    components: [nartis_rf_meter]
    refresh: 1s

nartis_rf_meter:
  radio:
    type: cmt2300a
    pin_sdio: GPIO23
    pin_sclk: GPIO18
    pin_csb: GPIO27
    pin_fcsb: GPIO26
    pin_gpio3: GPIO14

  meter_serial: "012345678901"   # 12 цифр с шильдика счётчика
  
  update_interval: 5min

sensor:
  - platform: nartis_rf_meter
    name: "Active Power"   # Активная мощность
    obis_code: "1.0.1.7.0.255"
    unit_of_measurement: W
    accuracy_decimals: 1
    device_class: power
    state_class: measurement
```

# Как это работает

1. По интервалу `update_interval` запускается цикл опроса.
2. Если сопряжение ещё не выполнено - компонент сканирует каналы по RSSI, выбирает канал и проходит handshake со счётчиком, получая сессионный ключ.
3. Если сопряжение уже есть - ключ и счётчики кадров переиспользуются, и сразу запускается чтение данных.
4. Запрашиваются настроенные сенсоры (по одному или пакетами `batch_size`), значения публикуются в Home Assistant.
5. По завершении цикла радио засыпает до следующего интервала.

> **О протоколе.** Это проприетарный протокол, построенный на идеях беспроводного M-Bus (wM-Bus, EN 13757): структура кадра (поля длины/контроля, адрес «производитель+серийник+версия+тип», CI-поле), коды функций control-поля и CRC-полином `0x3D65` заимствованы из wM-Bus, поверх - прикладной уровень DLMS/COSEM. Радиоуровень (433 МГц, CMT2300A или CC1101), шифрование (AES-128-GCM) и процедура сопряжения - собственные, поэтому стандартными wM-Bus-стэками счётчик не читается.

# Конфигурация хаба (`nartis_rf_meter`)

| Параметр                      | Тип / по умолчанию | Описание                                                                                       |
|-------------------------------|--------------------|------------------------------------------------------------------------------------------------|
| `radio`                       | блок, обязательно  | Радиомодуль и его выводы: `type: cmt2300a` или `type: cc1101` (см. раздел выше).                |
| `meter_serial`                | строка, обязательно| 12-значный серийный номер счётчика с шильдика (например `"021245003137"`).                     |
| `update_interval`             | время, `5min`      | Период опроса счётчика.                                                                        |
| `fix_channel`                 | 0...3, опц.          | Зафиксировать радиоканал и отключить авто-выбор по RSSI.                                       |
| `use_alternative_channels`    | bool, `false`      | Использовать альтернативную сетку частот - иногда помогает, если счётчик не отвечает.          |
| `batch_size`                  | 1...10, `5`          | Сколько OBIS-атрибутов читать одним запросом get-request-with-list.                            |
| `rx_timeout`                  | время, `3000ms`    | Общий таймаут ожидания ответа (сопряжение и завершение приёма кадра).                          |
| `rx_reply_timeout`            | время, `900ms`     | Короткий таймаут ожидания ответа на GET - до прихода первого байта.                            |


## Старый формат: выводы на верхнем уровне

До появления `radio:` пять выводов CMT2300A задавались прямо в блоке компонента.
Такие конфигурации **продолжают работать**: компонент сам сворачивает их в неявный
`radio: {type: cmt2300a, ...}` и печатает в лог предупреждение с новым написанием.

```yaml
# устарело, но работает
nartis_rf_meter:
  meter_serial: "012345678901"
  pin_sdio: GPIO23
  pin_sclk: GPIO18
  pin_csb: GPIO27
  pin_fcsb: GPIO26
  pin_gpio3: GPIO14
```

Ограничения совместимости:

- старые ключи и `radio:` **взаимоисключающи** - одновременно их указать нельзя;
- все пять `pin_*` обязаны быть заданы вместе, иначе будет понятная ошибка;
- в новых конфигурациях используйте только `radio:` - плоские ключи будут удалены.


# Сенсоры

### Числовой сенсор (sensor)

```yaml
sensor:
  - platform: nartis_rf_meter
    name: "Voltage L1"   # Напряжение фазы 1
    obis_code: "1.0.32.7.0.255"
    unit_of_measurement: V
    accuracy_decimals: 1
    device_class: voltage
    state_class: measurement
    filters:
      - multiply: 0.1   # при необходимости масштабируйте значение фильтром
```

Параметры: `obis_code` (обязательно), `obis_class` (по умолчанию `3`), `obis_attr` (по умолчанию `2`). Поддерживаются форматы OBIS `1.0.32.7.0.255`, `1-0:32.7.0.255`, `1-0:32.7.0*255`.

### Текстовый сенсор (text_sensor)

```yaml
text_sensor:
  - platform: nartis_rf_meter
    name: "Serial Number"   # Серийный номер
    obis_code: "0.0.96.1.0.255"
```

Octet-string данные декодируются как текст (байты - это коды символов: `30 32 33 ...` -> `"023..."`). Завершающие нулевые байты отбрасываются, управляющие байты (< 0x20) заменяются на `.`. Текстовые значения счётчика приходят в кодировке **CP1251** и автоматически конвертируются в **UTF-8**, поэтому кириллица (название, модель, производитель) отображается корректно.

Для объекта **Clock (класс 8)** укажите `obis_class: 8` - значение времени будет отформатировано как `ГГГГ-ММ-ДД ЧЧ:ММ:СС[.сс][ +/-ЧЧ:ММ]`:

```yaml
text_sensor:
  - platform: nartis_rf_meter
    name: "Meter Clock"   # Часы счётчика
    obis_code: "0.0.1.0.0.255"
    obis_class: 8
```

### Кнопка повторного сопряжения (button)

Кнопка в Home Assistant сбрасывает сохранённую сессию и запускает сопряжение заново - на случай, если связь со счётчиком «застряла». Запрос выполняется после завершения текущего цикла, поэтому активный обмен не прерывается.

```yaml
button:
  - platform: nartis_rf_meter
    name: "Re-pair"   # Повторное сопряжение
```

# Диагностика и советы

- **Счётчик не отвечает / нет сопряжения.** Попробуйте `use_alternative_channels: true` либо зафиксируйте канал `fix_channel: 0...3`. Проверьте антенну и питание модуля.
- **CC1101: счётчик не слышит нас.** Передатчик здесь на ~4 дБ слабее настоящего дисплея. Убедитесь, что `output_power` не занижен (по умолчанию `10` - это максимум чипа), и попробуйте `modulation: gfsk` - именно так модулирует настоящий Д101. Радикальное лечение - модуль с внешним усилителем (PA).
- **CC1101: байты приходят, но CRC не сходится.** Попробуйте `foc_carrier_sense_gate: true` и сравните долю ответов с верной CRC при обоих значениях. Менять `sync_word` здесь не нужно: байты в FIFO означают, что коррелятор уже нашёл синхрослово.
- **CC1101: не принимается вообще ничего.** Ни байта, ни при каком `foc_carrier_sense_gate`, а передача при этом проходит. Это единственный случай, когда стоит попробовать `sync_word: 0x72F6` - обратный порядок байт синхрослова (см. выше). Строка `Sync: ...` в логе при старте показывает, что реально запрограммировано.
- **CC1101: подстройка частоты приёма.** Приёмник и передатчик настраиваются независимо; при старте в лог печатаются обе частоты. Сдвинуть приём можно ключом `rx_offset` (со знаком, в герцах).
- **Проверьте серийный номер.** `meter_serial` - ровно 12 цифр с шильдика; из него выводится стартовый ключ шифрования и адресация.
- **Логи.** Включите подробный вывод, чтобы видеть переходы состояний и дампы кадров:

  ```yaml
  logger:
    level: VERY_VERBOSE
    tx_buffer_size: 2048 # длинные кадры могут обрезаться на выводе без этой настройки
  ```

- **Повторное сопряжение.** Если связь со счётчиком теряется, после нескольких неудачных чтений подряд компонент сам делает повторное сопряжение на следующем интервале.
